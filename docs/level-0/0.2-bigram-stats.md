# Уровень 0 — этап 0.2: Statistical Bigram Model

## Цель этапа

На этапе 0.2 RustLLM впервые извлекает информацию из обучающего текста.

После токенизации корпус представлен последовательностью `TokenId`. `BigramStats` считает, какие токены встречаются непосредственно друг после друга, а затем позволяет преобразовать эти наблюдения в эмпирические вероятности следующего токена.

```text
text
  ↓
CharTokenizer
  ↓
[TokenId, TokenId, ...]
  ↓
BigramStats::observe
  ↓
transition counts
  ↓
probabilities
```

Это ещё не нейронная сеть и не обучаемая матрица весов. На этом этапе модель строится непосредственно из статистики корпуса.

---

## 1. Что такое bigram

Bigram — пара соседних токенов.

Для последовательности:

```text
[A, B, C, D]
```

получаем три биграммы:

```text
A -> B
B -> C
C -> D
```

В общем случае последовательность из `N` токенов содержит:

```text
N - 1
```

соседних переходов, если `N >= 1`.

Поэтому:

```text
[]      -> 0 переходов
[A]     -> 0 переходов
[A, B]  -> 1 переход
```

---

## 2. Что именно хранит `BigramStats`

Для vocabulary размера `V` существует `V` возможных текущих токенов и `V` возможных следующих токенов.

Следовательно, существует:

```text
V × V
```

возможных переходов.

`BigramStats` хранит число наблюдений для каждого из них.

Логически это матрица:

```text
                    next token
                 0     1     2
               ┌────────────────
current  0     │  0     3     1
 token   1     │  2     0     4
         2     │  1     5     0
```

Ячейка `(i, j)` означает:

```text
сколько раз токен j встретился сразу после токена i
```

Обозначим это как:

```text
C(i, j)
```

где `C` — count.

---

## 3. Почему матрица хранится в одном `Vec<u64>`

Вместо:

```rust
Vec<Vec<u64>>
```

текущая реализация использует:

```rust
Vec<u64>
```

Матрица укладывается в память строка за строкой — **row-major order**.

Матрица:

```text
0 1
1 1
```

физически хранится как:

```text
[0, 1, 1, 1]
```

Такой формат важен не только для bigram-статистики. Позже похожим образом будут храниться матрицы весов и tensor buffers.

---

## 4. Преобразование двумерного индекса в плоский

Пусть:

```text
row    = current
column = next
width  = vocab_size = V
```

Тогда индекс в плоском массиве:

```text
index = row * V + column
```

### Откуда берётся формула

Если ширина строки `V`, то перед строкой `row` находится:

```text
row * V
```

элементов.

После этого остаётся сместиться на номер столбца:

```text
+ column
```

Например для `V = 3`:

```text
      0   1   2
    ┌───────────
0   │ 0   1   2
1   │ 3   4   5
2   │ 6   7   8
```

Для:

```text
row = 1
column = 2
```

получаем:

```text
1 * 3 + 2 = 5
```

---

## 5. Пример `abba`

Пусть tokenizer назначил:

```text
a -> TokenId(0)
b -> TokenId(1)
```

Тогда:

```text
"abba"
   ↓
[0, 1, 1, 0]
```

Соседние переходы:

```text
0 -> 1
1 -> 1
1 -> 0
```

Начальная матрица:

```text
      next
       a  b
     ┌──────
a    │ 0  0
b    │ 0  0
```

После наблюдения `abba`:

```text
      next
       a  b
     ┌──────
a    │ 0  1
b    │ 1  1
```

В row-major представлении:

```text
[0, 1, 1, 1]
```

То есть:

```text
C(a, a) = 0
C(a, b) = 1
C(b, a) = 1
C(b, b) = 1
```

---

## 6. `BigramStats::new`

Создаёт пустую матрицу переходов для vocabulary размера `V`.

Контракт:

```text
V == 0
    -> EmptyVocabulary

V > 0
    -> создать V * V счётчиков
    -> каждый счётчик равен 0
```

Умножение выполняется через checked arithmetic:

```rust
vocab_size.checked_mul(vocab_size)
```

Это предотвращает переполнение `usize` при вычислении размера матрицы.

После успешного `new(V)` выполняются инварианты:

```text
counts.len() == V * V
```

и:

```text
для каждого count: count == 0
```

---

## 7. Валидация `TokenId`

Сам факт существования `TokenId` не означает, что он принадлежит vocabulary конкретного `BigramStats`.

Например:

```text
vocab_size = 2
TokenId(100)
```

может быть корректным значением типа `TokenId`, но не является допустимым токеном для этой статистики.

`validate_token()` выполняет два шага:

1. преобразует `TokenId` в `usize`;
2. проверяет условие:

```text
index < vocab_size
```

При успехе возвращает уже проверенный индекс vocabulary.

При нарушении границы возвращает:

```text
TokenOutOfVocabulary
```

Эта проверка вынесена в отдельный helper, чтобы `index()`, `probabilities()` и будущие методы не дублировали одну и ту же логику.

---

## 8. `index(current, next)`

`index()` преобразует пару токенов в позицию соответствующего счётчика в плоской матрице.

Контракт:

```text
(current, next)
       ↓
validate current
validate next
       ↓
current * V + next
       ↓
usize
```

Для `V = 2`:

```text
(0, 0) -> 0
(0, 1) -> 1
(1, 0) -> 2
(1, 1) -> 3
```

Это проверяется отдельным unit-тестом на row-major layout.

---

## 9. `count(current, next)`

`count()` возвращает число уже наблюдённых переходов:

```text
C(current, next)
```

Метод не повторяет проверку токенов самостоятельно. Он использует `index()`, который централизованно выполняет валидацию и адресацию.

Получается цепочка:

```text
count()
   ↓
index()
   ↓
validate_token()
```

Это уменьшает дублирование логики и число мест, где могут появиться разные правила проверки.

---

## 10. `observe(tokens)`

`observe()` добавляет статистику соседних токенов из переданной последовательности.

Для:

```text
[A, B, C, D]
```

необходимо увеличить счётчики:

```text
A -> B
B -> C
C -> D
```

В Rust последовательность соседних пар удобно получать через:

```rust
tokens.windows(2)
```

Для каждого окна длины 2:

1. взять `current` и `next`;
2. получить индекс через `index()`;
3. увеличить соответствующий `count` на единицу.

Сложение должно быть проверяемым:

```rust
checked_add(1)
```

чтобы переполнение `u64` превращалось в `BigramStatsError::CountOverflow`, а не в panic или wraparound.

### Накопительная семантика

`observe()` не сбрасывает ранее собранные значения.

Поэтому:

```text
observe(A)
observe(B)
```

накапливает статистику обоих наборов данных.

Это позволяет в будущем подавать corpus частями или потоками.

### Пустой ввод

```text
observe([])
observe([A])
```

не являются ошибками и не меняют статистику, потому что в этих последовательностях нет ни одной пары соседних токенов.

### Ошибка во время обработки

На уровне 0 используется простая streaming-семантика: если ошибка возникла после нескольких успешно обработанных переходов, уже внесённые изменения не откатываются.

Транзакционное поведение здесь намеренно не реализуется.

---

## 11. От counts к probabilities

Counts показывают абсолютную частоту событий. Для генерации текста нужны вероятности.

Допустим после токена `b` наблюдалось:

```text
b -> a : 3
b -> b : 1
b -> c : 0
```

Общее число исходящих переходов:

```text
3 + 1 + 0 = 4
```

Тогда вероятности:

```text
P(a | b) = 3 / 4 = 0.75
P(b | b) = 1 / 4 = 0.25
P(c | b) = 0 / 4 = 0.00
```

Общая формула:

```text
P(j | i) = C(i, j) / sum_k C(i, k)
```

Читается как:

> вероятность следующего токена `j` при условии, что текущий токен — `i`.

Здесь:

```text
C(i, j)
```

— число наблюдений конкретного перехода, а:

```text
sum_k C(i, k)
```

— сумма всех исходящих переходов из `i`.

---

## 12. Почему сумма вероятностей равна 1

Если учтены все возможные следующие токены, один из них должен быть выбран.

Поэтому:

```text
P(token_0 | current)
+ P(token_1 | current)
+ ...
+ P(token_V-1 | current)
≈ 1.0
```

Используется `≈`, а не строгое `==`, потому что `f64` хранит многие дроби приближённо.

Например `1 / 3` невозможно представить конечной двоичной дробью без погрешности.

Поэтому тесты floating-point результатов должны использовать допустимую погрешность `epsilon`, например:

```text
abs(sum - 1.0) < epsilon
```

---

## 13. Нет исходящих переходов

Если текущий токен встречался только в конце последовательности, после него не наблюдалось ни одного следующего токена.

Тогда строка counts может быть:

```text
[0, 0, 0]
```

и знаменатель вероятности равен нулю.

Операция:

```text
0 / 0
```

не определяет корректное распределение вероятностей.

Поэтому текущий контракт возвращает:

```text
BigramStatsError::NoOutgoingTransitions(token)
```

На этом этапе не применяется smoothing и не подставляется искусственное равномерное распределение.

---

## 14. Bigram как языковая модель

Bigram-модель оценивает:

```text
P(next_token | current_token)
```

То есть при выборе следующего токена она учитывает ровно один предыдущий токен.

Это можно рассматривать как простейшее состояние Markov-модели первого порядка:

```text
следующее состояние зависит только от текущего состояния
```

Модель не знает более длинного контекста.

Например, если текущий символ одинаков, для неё не существует различия между двумя совершенно разными предшествующими фразами.

Это фундаментальное ограничение bigram-подхода, но именно поэтому он удобен для изучения механики языкового моделирования.

---

## 15. Связь с будущим Transformer

Статистический bigram и современная LLM очень различаются по способу вычисления вероятностей, но решают родственную конечную задачу:

```text
какой токен должен идти следующим?
```

Bigram:

```text
P(next | current)
```

Transformer:

```text
P(next | previous context)
```

Позже вместо прямых counts появятся:

- обучаемые веса;
- logits;
- softmax;
- loss;
- gradient descent;
- embeddings;
- attention.

Но понятие **распределения вероятностей следующего токена** останется центральным.

---

## 16. Ошибки `BigramStats`

### `EmptyVocabulary`

Нельзя создать таблицу переходов для vocabulary размера `0`.

### `MatrixSizeOverflow`

`V * V` не помещается в `usize`, поэтому матрицу требуемого размера невозможно корректно адресовать.

### `TokenIndexToUsizeOverflow`

Значение `TokenId` невозможно представить как `usize` на текущей платформе.

### `TokenOutOfVocabulary`

`TokenId` численно существует, но его индекс не удовлетворяет:

```text
index < vocab_size
```

### `IndexSizeOverflow`

Вычисление плоского row-major индекса не помещается в `usize`.

При корректно созданной матрице и валидных токенах этот вариант должен быть практически недостижим и служит дополнительной защитой арифметики.

### `CountOverflow`

Счётчик конкретного перехода уже равен `u64::MAX` и не может быть увеличен ещё на единицу.

### `NoOutgoingTransitions`

Для текущего токена нет ни одного наблюдённого следующего токена, поэтому нельзя построить эмпирическое распределение вероятностей.

## 17. Инварианты этапа 0.2

После успешного создания:

```text
counts.len() == V * V
```

Все counts неотрицательны, что естественно обеспечивается типом `u64`.

Для валидного токена:

```text
0 <= token.index() < V
```

После наблюдения последовательности из `N >= 1` токенов на изначально пустой статистике:

```text
sum(counts) == N - 1
```

если обработка завершилась без ошибки.

Для строки probabilities с хотя бы одним наблюдением:

```text
0.0 <= p_j <= 1.0
```

и:

```text
sum(probabilities) ≈ 1.0
```

Длина распределения:

```text
probabilities.len() == V
```

---

## 18. Тестовый минимум этапа

Статистическая часть этапа должна проверять как минимум:

- создание нулевой матрицы;
- отказ от пустого vocabulary;
- правильный row-major index;
- отказ для невалидного `current`;
- отказ для невалидного `next`;
- корректный подсчёт биграмм;
- накопление counts несколькими вызовами `observe()`;
- корректную обработку `[]`;
- корректную обработку `[A]`;
- нормализацию probabilities;
- сумму probabilities около `1.0`;
- ошибку при отсутствии исходящих переходов.

Удобный эталонный corpus:

```text
abba
```

Ожидаемые counts:

```text
[0, 1,
 1, 1]
```

Ожидаемые вероятности:

```text
P(a | a) = 0.0
P(b | a) = 1.0

P(a | b) = 0.5
P(b | b) = 0.5
```

---

## 19. Что намеренно не входит в статистическую часть 0.2

Пока не нужны:

- trainable weights;
- logits;
- softmax;
- cross-entropy loss;
- gradients;
- learning rate;
- optimizer;
- smoothing;
- temperature;
- top-k/top-p.

Сначала необходимо полностью понять цепочку:

```text
tokens
  -> neighboring pairs
  -> counts
  -> probabilities
```

После этого sampling сможет превратить распределение вероятностей в выбор следующего `TokenId`, а generation loop — повторять этот процесс для генерации последовательности.
