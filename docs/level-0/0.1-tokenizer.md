# Уровень 0 — этап 0.1: Character-level tokenizer

## Цель этапа

На этапе 0.1 RustLLM получает границу между текстом и внутренним представлением модели.

Модель не работает напрямую со строками или символами. Перед обработкой текст необходимо преобразовать в последовательность числовых идентификаторов — токенов. Обратное преобразование позволяет снова получить текст.

```text
"Привет"
    │
    ▼
CharTokenizer::encode
    │
    ▼
[TokenId(...), TokenId(...), ...]
    │
    ▼
внутреннее представление модели
```

Обратное направление:

```text
[TokenId(...), TokenId(...), ...]
    │
    ▼
CharTokenizer::decode
    │
    ▼
"Привет"
```

На этом уровне используется **character-level tokenizer**: один Unicode `char` соответствует одному токену.

---

## 1. Основные понятия

### Token

Токен — минимальная единица текста, с которой работает модель.

В текущей реализации:

```text
один Rust char = один токен
```

Например:

```text
"abba"
```

содержит четыре позиции токенов:

```text
a, b, b, a
```

При этом vocabulary содержит только два уникальных токена:

```text
a, b
```

### Vocabulary

Vocabulary — множество всех токенов, известных токенизатору.

Если corpus равен:

```text
"caba"
```

уникальные символы:

```text
a, b, c
```

и размер vocabulary:

```text
V = 3
```

В RustLLM vocabulary строится детерминированно: символы собираются в `BTreeSet<char>`, поэтому порядок определяется сортировкой символов, а не порядком их первого появления в корпусе.

Например для корпуса:

```text
"cba"
```

идентификаторы всё равно будут назначены как:

```text
a -> 0
b -> 1
c -> 2
```

Это важный инвариант: одинаковый набор символов приводит к одинаковому отображению `char <-> TokenId`.

---

## 2. `TokenId`

```rust
pub struct TokenId(u32);
```

`TokenId` — компактный тип-обёртка над числовым идентификатором токена.

Отдельный тип полезнее обычного `u32`, потому что не позволяет случайно смешивать идентификатор токена с другими числами программы.

### `TokenId::from_index`

Преобразует индекс `usize` в `TokenId`:

```text
usize -> Option<TokenId>
```

`TokenId` хранит `u32`, поэтому индекс может быть представлен не на всех теоретически возможных платформах и для всех значений `usize`.

`None` означает, что значение не помещается в `u32`.

### `TokenId::index`

Преобразует `TokenId` обратно в индекс, пригодный для обращения к Rust-коллекциям:

```text
TokenId -> Option<usize>
```

`None` означает, что внутреннее значение `u32` невозможно представить как `usize` на текущей платформе.

---

## 3. Устройство `CharTokenizer`

```rust
pub struct CharTokenizer {
    char_to_id: HashMap<char, TokenId>,
    id_to_char: Vec<char>,
}
```

Используются два отображения.

### `char_to_id`

```text
char -> TokenId
```

Нужно для `encode()`.

Например:

```text
'a' -> TokenId(0)
'b' -> TokenId(1)
```

### `id_to_char`

```text
TokenId -> char
```

Нужно для `decode()`.

Идентификатор одновременно является индексом `Vec<char>`:

```text
id_to_char[0] == 'a'
id_to_char[1] == 'b'
```

Два представления позволяют выполнять преобразования в обоих направлениях без линейного поиска по vocabulary.

---

## 4. Построение vocabulary

`CharTokenizer::from_corpus(corpus)` выполняет три логических действия:

1. получает множество уникальных Unicode-символов корпуса;
2. задаёт им детерминированный порядок;
3. назначает идентификаторы `0..V`.

Для:

```text
corpus = "caba"
```

получаем:

```text
unique = ['a', 'b', 'c']
```

затем:

```text
'a' -> TokenId(0)
'b' -> TokenId(1)
'c' -> TokenId(2)
```

В результате:

```text
char_to_id = {
    'a': 0,
    'b': 1,
    'c': 2,
}

id_to_char = ['a', 'b', 'c']
```

### Почему `BTreeSet`

`HashSet` хорошо подходит для уникальности, но не гарантирует удобный стабильный порядок обхода.

`BTreeSet` одновременно:

- удаляет дубликаты;
- сортирует элементы;
- делает назначение `TokenId` детерминированным.

На этом учебном этапе предсказуемость важнее потенциальной разницы в производительности.

---

## 5. Encoding

Контракт:

```text
text -> Result<Vec<TokenId>, TokenizerError>
```

Для каждого `char`:

1. найти его в `char_to_id`;
2. получить соответствующий `TokenId`;
3. добавить идентификатор в выходную последовательность.

Пример:

```text
Vocabulary:
a -> 0
b -> 1

"abba"
   ↓
[0, 1, 1, 0]
```

Если символ отсутствует в vocabulary, возвращается:

```text
TokenizerError::UnknownChar(ch)
```

Токенизатор не добавляет неизвестный символ автоматически, потому что это изменило бы vocabulary и нарушило соответствие модели её размерности.

---

## 6. Decoding

Контракт:

```text
&[TokenId] -> Result<String, TokenizerError>
```

Для каждого `TokenId`:

1. преобразовать его в `usize`;
2. использовать индекс для доступа к `id_to_char`;
3. добавить найденный `char` в выходную строку.

Пример:

```text
[0, 1, 1, 0]
   ↓
"abba"
```

Если идентификатор находится за пределами vocabulary, возвращается:

```text
TokenizerError::UnknownTokenId(id)
```

---

## 7. Round-trip

Главный функциональный инвариант токенизатора:

```text
decode(encode(text)) == text
```

при условии, что все символы `text` входят в vocabulary токенизатора.

Это называется **round-trip**.

В RustLLM он проверяется отдельно для:

- ASCII;
- кириллицы;
- смешанного UTF-8 текста.

Character-level подход удобен здесь тем, что Rust `char` представляет Unicode scalar value, поэтому мы не разбираем строку побайтово.

---

## 8. Bytes, chars и tokens

Эти величины нельзя считать одним и тем же.

Например UTF-8 символ может занимать несколько байт:

```text
bytes count != chars count
```

В текущем character-level tokenizer:

```text
chars count == tokens count
```

для закодированного текста.

Но это свойство именно текущей реализации. После перехода к subword tokenizer один токен сможет представлять несколько символов, и равенство исчезнет.

---

## 9. Ошибки этапа 0.1

### `UnknownChar(char)`

Попытка закодировать символ, которого нет в vocabulary.

### `UnknownTokenId(TokenId)`

Попытка декодировать идентификатор за пределами vocabulary.

### `TokenIdPosOverflow`

Позиция нового токена в vocabulary не помещается во внутренний `u32` типа `TokenId`.

### `TokenIdToUsizeOverflow`

Внутренний `TokenId` невозможно представить как `usize` текущей платформы.

---

## 10. Инварианты этапа

После успешного создания `CharTokenizer` должны выполняться условия:

```text
char_to_id.len() == id_to_char.len()
```

```text
vocab_size() == id_to_char.len()
```

Каждый символ vocabulary имеет ровно один `TokenId`.

Каждый валидный `TokenId` соответствует ровно одному символу.

Для поддерживаемого текста:

```text
decode(encode(text)) == text
```

Порядок назначения идентификаторов детерминирован.

---

## 11. Что намеренно не входит в 0.1

На этом этапе не реализуются:

- BPE;
- WordPiece;
- Unigram tokenizer;
- специальные токены BOS/EOS/PAD/UNK;
- нормализация Unicode;
- сериализация vocabulary;
- обучение subword vocabulary;
- byte-level tokenization.

Сейчас задача — понять сам контракт:

```text
текст <-> токены
```

и получить надёжную основу для следующих компонентов модели.

---

## 12. Связь со следующим этапом

После токенизации модель впервые может работать не с текстом, а с последовательностью целых идентификаторов.

Для:

```text
"abba"
```

токенизатор выдаёт:

```text
[0, 1, 1, 0]
```

На этапе 0.2 эта последовательность превращается в наблюдения соседних переходов:

```text
0 -> 1
1 -> 1
1 -> 0
```

То есть tokenizer отвечает за **представление**, а `BigramStats` — уже за **извлечение статистики из последовательности**.
