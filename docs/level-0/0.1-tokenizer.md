# Уровень 0 — этап 0.1: Character-level tokenizer

## Цель

На этапе 0.1 RustLLM получает границу между человеческим текстом и внутренним числовым представлением модели.

Модель не работает непосредственно со строками. Перед дальнейшей обработкой текст преобразуется в последовательность идентификаторов `TokenId`, а обратное преобразование позволяет восстановить исходный текст.

---

## Место в pipeline

Прямое преобразование:

```text
text
  ↓
CharTokenizer::encode
  ↓
Vec<TokenId>
  ↓
внутреннее представление модели
```

Обратное преобразование:

```text
Vec<TokenId>
  ↓
CharTokenizer::decode
  ↓
text
```

На этапе 0.1 используется **character-level tokenizer**:

```text
1 Unicode char = 1 token
```

---

## Основные понятия

### Token

Токен — минимальная единица текста, с которой работает модель.

Для строки:

```text
"abba"
```

текущая реализация видит четыре позиции токенов:

```text
a, b, b, a
```

### Vocabulary

Vocabulary — множество всех токенов, известных токенизатору.

Для корпуса:

```text
"caba"
```

уникальные символы:

```text
a, b, c
```

Размер vocabulary:

```text
V = 3
```

где `V` — число уникальных токенов.

### Детерминированное vocabulary

В RustLLM символы собираются в `BTreeSet<char>`, поэтому перед назначением идентификаторов они находятся в стабильном отсортированном порядке.

Например:

```text
corpus = "cba"
```

даёт:

```text
a -> TokenId(0)
b -> TokenId(1)
c -> TokenId(2)
```

Порядок первого появления символов в corpus не влияет на назначение идентификаторов.

---

## Математика и представление данных

На этом этапе сложная математика не требуется.

Важно различать:

```text
bytes
chars
tokens
```

Для UTF-8:

```text
bytes count != chars count
```

Например кириллический символ занимает несколько байт, но является одним Rust `char`.

В текущем character-level tokenizer:

```text
chars count == tokens count
```

Это свойство именно текущей реализации. После перехода к subword-tokenization один токен сможет представлять несколько символов.

---

## Контракт

### `TokenId`

```rust
pub struct TokenId(u32);
```

`TokenId` — отдельный тип-обёртка над числовым идентификатором токена.

Отдельный тип не позволяет случайно смешивать идентификаторы токенов с другими числовыми значениями программы.

### `TokenId::from_index`

```text
usize -> Option<TokenId>
```

Преобразует индекс vocabulary в `TokenId`.

`None` означает, что значение `usize` не помещается во внутреннее представление `u32`.

### `TokenId::index`

```text
TokenId -> Option<usize>
```

Преобразует `TokenId` в индекс, пригодный для обращения к Rust-коллекциям.

`None` означает, что внутреннее значение невозможно представить как `usize` на текущей платформе.

### `CharTokenizer::from_corpus`

Строит tokenizer по уникальным символам `corpus`.

Логически:

```text
corpus
  ↓
unique chars
  ↓
sorted chars
  ↓
TokenId 0..V
```

### `CharTokenizer::encode`

```text
&str -> Result<Vec<TokenId>, TokenizerError>
```

Преобразует текст в последовательность токенов.

Порядок `TokenId` совпадает с порядком символов исходного текста.

### `CharTokenizer::decode`

```text
&[TokenId] -> Result<String, TokenizerError>
```

Преобразует последовательность токенов обратно в строку.

### `CharTokenizer::vocab_size`

Возвращает количество токенов в vocabulary:

```text
V
```

## Реализация

`CharTokenizer` использует два отображения:

```rust
pub struct CharTokenizer {
    char_to_id: HashMap<char, TokenId>,
    id_to_char: Vec<char>,
}
```

### `char_to_id`

Используется при encoding:

```text
char -> TokenId
```

Например:

```text
'a' -> TokenId(0)
'b' -> TokenId(1)
```

### `id_to_char`

Используется при decoding:

```text
TokenId -> char
```

Идентификатор одновременно является индексом `Vec<char>`:

```text
id_to_char[0] == 'a'
id_to_char[1] == 'b'
```

Два отображения позволяют выполнять преобразования в обоих направлениях без линейного поиска.

### Почему `BTreeSet`

`BTreeSet` одновременно:

- удаляет дубликаты;
- сортирует символы;
- делает назначение `TokenId` детерминированным.

На текущем учебном этапе предсказуемость результата важнее потенциальной разницы в производительности относительно других структур.

---

## Ошибки

### `UnknownChar(char)`

Попытка закодировать символ, отсутствующий в vocabulary.

### `UnknownTokenId(TokenId)`

Попытка декодировать идентификатор, отсутствующий в vocabulary.

### `TokenIdPosOverflow`

Vocabulary содержит больше токенов, чем может представить внутренний `u32` типа `TokenId`.

### `TokenIdToUsizeOverflow`

Значение `TokenId` невозможно представить как `usize` на текущей платформе.

---

## Инварианты

После успешного создания tokenizer:

```text
char_to_id.len() == id_to_char.len()
```

```text
vocab_size() == id_to_char.len()
```

Каждый символ vocabulary имеет ровно один `TokenId`.

Каждый валидный `TokenId` соответствует ровно одному символу.

Главный функциональный инвариант:

```text
decode(encode(text)) == text
```

если все символы `text` входят в vocabulary.

Назначение идентификаторов детерминировано.

---

## Тесты

Этап 0.1 должен проверять как минимум:

- ASCII round-trip;
- round-trip для кириллицы;
- round-trip для смешанного UTF-8;
- детерминированные `TokenId`;
- ошибку для неизвестного символа;
- ошибку для неизвестного `TokenId`.

---

## Что намеренно не входит в этап

На этапе 0.1 не реализуются:

- BPE;
- WordPiece;
- Unigram tokenizer;
- byte-level tokenization;
- специальные токены BOS/EOS/PAD/UNK;
- Unicode normalization;
- сериализация vocabulary;
- обучение subword vocabulary.

---

## Что важно понять

После этапа 0.1 нужно понимать:

- зачем модели числовое представление текста;
- чем отличаются `bytes`, `chars` и `tokens`;
- что такое vocabulary;
- зачем нужен отдельный тип `TokenId`;
- почему детерминированное отображение важно;
- что означает round-trip.

## Следующий шаг

После tokenization:

```text
"abba"
  ↓
[0, 1, 1, 0]
```

RustLLM уже может работать с последовательностью чисел.

На этапе 0.2 эта последовательность начинает использоваться как обучающие данные для статистической bigram-модели.
