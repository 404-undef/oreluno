# Уровень 0 — этап 0.2.5: Deterministic PRNG

## Цель

На подэтапе 0.2.5 RustLLM получает собственный детерминированный генератор
псевдослучайных чисел и абстракцию `RandomSource`.

PRNG нужен для sampling: распределение вероятностей само по себе не выбирает
следующий токен. Для выбора требуется число в диапазоне:

```text
0.0 <= random < 1.0
```

Pipeline после этого подэтапа:

```text
seed
  ↓
Rng
  ↓
RandomSource::next_f64()
  ↓
random ∈ [0.0, 1.0)
  ↓
sample_index()
  ↓
next token index
```

---

## Детерминированность

PRNG не создаёт истинную случайность. Последовательность полностью определяется:

```text
seed + algorithm
```

Поэтому одинаковый `seed` даёт одинаковую последовательность значений.

Это важно для:

- воспроизводимости генерации;
- тестов;
- отладки;
- сравнения поведения модели после изменений.

Если `--seed` не указан, текущий CLI использует значение `0`.

---

## SplitMix64

Учебная реализация `Rng` основана на SplitMix64.

Состояние генератора:

```rust
state: u64
```

При каждом вызове `next_u64()` выполняются две логически разные операции:

```text
1. переход к следующему состоянию;
2. перемешивание битов состояния.
```

### Переход состояния

```text
state = state + 0x9E3779B97F4A7C15  (mod 2^64)
```

В Rust используется:

```rust
wrapping_add
```

Переполнение здесь является частью алгоритма, а не ошибкой.

Константа:

```text
0x9E3779B97F4A7C15
```

часто называется `GOLDEN_GAMMA`. Она связана с золотым сечением и используется
как шаг 64-битной Weyl-последовательности.

Константа нечётная, поэтому она взаимно проста с `2^64`. При сложении по модулю
`2^64` это позволяет пройти все возможные 64-битные состояния до повторения.

---

## Перемешивание состояния

После изменения состояния применяется 64-битная функция перемешивания
Stafford variant 13:

```text
z = state
z = (z XOR (z >> 30)) * 0xBF58476D1CE4E5B9
z = (z XOR (z >> 27)) * 0x94D049BB133111EB
z = z XOR (z >> 31)
```

Умножения выполняются через:

```rust
wrapping_mul
```

то есть по модулю `2^64`.

### Почему `30`, `27` и `31`

Эти значения не выводятся независимо из размера `u64`.

Сдвиги:

```text
30
27
31
```

и множители:

```text
0xBF58476D1CE4E5B9
0x94D049BB133111EB
```

образуют специально подобранную функцию перемешивания и должны
рассматриваться как единая конструкция.

Операция:

```text
z XOR (z >> n)
```

заставляет биты из более старших позиций влиять на младшие. Последующие
умножения дополнительно распространяют изменения по 64-битному слову.

Цель такого mixer — хорошая диффузия: небольшое изменение входного состояния
должно существенно изменять выходное значение.

## `next_f64()`

Sampling ожидает не `u64`, а `f64` в полуинтервале:

```text
[0.0, 1.0)
```

`f64` имеет 53 бита точности значащей части, поэтому из 64-битного результата
используются 53 бита.

Число отбрасываемых битов:

```text
64 - 53 = 11
```

Отсюда:

```rust
self.next_u64() >> 11
```

После сдвига:

```text
0 <= value <= 2^53 - 1
```

Затем значение делится на:

```text
2^53
```

которое в коде выражается как:

```rust
1_u64 << 53
```

Поэтому:

```text
0 / 2^53 = 0.0
```

а максимальное значение:

```text
(2^53 - 1) / 2^53 < 1.0
```

Таким образом `1.0` не может быть возвращено по построению.

## `RandomSource`

Алгоритмы модели не должны зависеть от конкретной реализации PRNG.

Для этого введён минимальный контракт:

```rust
pub trait RandomSource {
    fn next_f64(&mut self) -> f64;
}
```

Контракт реализации:

```text
next_f64() -> [0.0, 1.0)
```

Текущий `Rng` реализует этот trait, но в будущем вместо него можно использовать:

- другой детерминированный PRNG;
- production-реализацию;
- источник, инициализированный энтропией ОС;
- контролируемый тестовый источник;
- пользовательскую реализацию.

`next_u64()` намеренно не входит в `RandomSource`: sampling-механизму нужен
только нормализованный `f64`, а способ его получения остаётся деталью
конкретного генератора.

---

## Почему RNG передаётся извне

Модель не хранит конкретный `Rng` внутри себя.

Вместо этого методы модели принимают:

```rust
&mut impl RandomSource
```

`&mut` требуется потому, что получение следующего псевдослучайного значения
изменяет внутреннее состояние генератора.

Такое разделение сохраняет независимость:

```text
модель
  ↓ зависит только от
RandomSource
  ↑ реализуется
Rng / другой PRNG / тестовый источник
```

---

## Тесты

Подэтап проверяет:

- одинаковый `seed` создаёт одинаковую последовательность `u64`;
- одинаковый `seed` создаёт одинаковую последовательность `f64`;
- `next_f64()` всегда возвращает значение в `[0.0, 1.0)`.

Дополнительно `RandomSource` используется в тестах `BigramModel` через
контролируемую реализацию, возвращающую заранее заданное значение.

---

## Что важно понять

После подэтапа 0.2.5 нужно понимать:

- разницу между истинной случайностью и PRNG;
- роль `seed`;
- почему детерминированность полезна;
- зачем SplitMix64 разделяет переход состояния и перемешивание;
- почему в алгоритме нужны `wrapping_add` и `wrapping_mul`;
- откуда берётся сдвиг `11` при преобразовании в `f64`;
- почему результат `next_f64()` принадлежит `[0.0, 1.0)`;
- зачем RNG скрыт за заменяемым контрактом `RandomSource`.

## Следующий шаг

Подэтап 0.2.6 объединяет готовые компоненты в цикл генерации:

```text
current TokenId
  ↓
BigramModel::next_token()
  ↓
next TokenId
  ↓
новый current
  ↓
повтор
```

Сначала модель уже умеет выбрать один следующий токен. Следующий шаг —
повторить эту операцию заданное число раз и получить последовательность
сгенерированных `TokenId`.
